# Test Health Audit — harness

Suite: 2201 tests, 0 failures, 66 integration excluded by default. 1 flaky test observed during this audit run (retried, passed).

## Critical

1. **`test/harness/lander/resolver_test.exs:51` — genuinely flaky, not just theoretically async-unsafe.** The retry-log capture (`/tmp/audit-cov.json`) shows this exact test failed on first attempt with `available: []` (empty registry) then passed on retry. The file's own top-of-module comment (lines 11-13) documents *why*: `AgentRegistry.set_installed/2` mutates the global `Harness.AgentRegistry` singleton via `:sys.replace_state`, "same class as ReviewerSelectionTest; observed 2026-07-07" — i.e. this is a **known, previously-observed cross-test pollution class that has not been fixed**, only annotated. `async: false` on the file prevents intra-file races but does not prevent another concurrently-running file (or a stale registry restart timing) from observing/mutating the same singleton mid-test. Action: either serialize all `AgentRegistry.set_installed/2`-mutating test files onto one `ExUnit` group/tag (e.g. a shared `:global_state` tag with `async: false` enforced suite-wide, or `Application.stop`/isolate the registry per test via `start_supervised!`), or refactor `AgentRegistry` mutation in tests to use a supervised per-test instance instead of `:sys.replace_state` on the shared singleton. Currently this is a live flake, not a hypothetical one.

2. **`Harness.Git.TargetSync` (`lib/harness/git/target_sync.ex`) has zero dedicated test coverage.** No `test/**/*target_sync*` file exists, and grep for `Harness.Git.TargetSync` in `test/` returns nothing. This module has three real branches (clean checked-out `merge --ff-only`, unchecked-out ref-only fetch, and dirty/diverged skip) plus a `behind_count` drift-message helper, and per its own moduledoc it is load-bearing for **both the autonomous lander and durable roadmap writes** — "skip it and roadmap/tasks.toml drifts behind origin and a later merge conflicts or silently loses the harness transition." A landing/merge-critical-path module with this much branching and zero unit tests is a coverage gap in exactly the area the project's own docs call out as high-stakes (see harness-workflow.md "Recover, Don't Redo" / duplicate-land incident).

## Warnings

3. **`Harness.Store.EtsScope` (`lib/harness/store/ets_scope.ex`) has no dedicated test file.** Grep for `Harness.Store.EtsScope` in `test/` finds nothing; only indirect exercise via other suites (if any) would cover it. Worth a direct unit test given ETS lifecycle/ownership modules are easy to get subtly wrong (table ownership on process death, race on create).

4. **Timing-based `Process.sleep` synchronization, real but bounded risk.** Most `Process.sleep` occurrences are either (a) deliberately simulating a wedged/slow process (`Process.sleep(:infinity)` in test doubles — legitimate) or (b) short fixed waits used as a poll/settle delay before assertion, e.g.:
   - `test/harness/worktree_test.exs:125,456` — `Process.sleep(30)` before asserting worktree state
   - `test/harness/status_view_test.exs:322` — `Process.sleep(20)`
   - `test/harness/chat/session_test.exs:373,398,404` — `Process.sleep(200/150/150)` around session state
   - `test/harness/dashboard/roadmap_summary_test.exs:193` — `Process.sleep(30)`
   - `test/harness/batch_test.exs:481,688,722`, `test/harness/project_registry_test.exs:839`, `test/harness/project_registry/persistence_test.exs:214`, `test/harness/oban_queue_bootstrap_test.exs:84`, `test/harness/worktree/reaper_test.exs:140` — all named `@eventually_delay_ms` (an explicit poll-loop constant, better than a bare literal, but still a fixed-sleep-then-assert pattern rather than `assert_receive`/monitor if the underlying signal is process-observable)
   None of these hit the CRITICAL iron-law violation shape (a sleep replacing a receivable message with no re-check), but several assert state *once* right after a fixed sleep rather than polling-until-true or using `assert_receive`. Under CI load these are the most plausible source of future flakes. Recommend auditing the `@eventually_delay_ms` call sites specifically — if they already retry-loop internally this is fine; if they assert once after one sleep, they're a latent flake.

5. **`test/harness/run/memory_guard_test.exs:30`** — `Process.sleep(25) && await_children(...)` used as a manual busy-poll inside a recursive helper rather than `assert_receive`/`Process.monitor`. Functionally a retry loop (bounded by `tries`), so lower risk than a bare sleep-then-assert, but still monitor-based synchronization would be more robust and faster.
